大厅显示自己的当前房间；已有占用时创建或加入别的房间会被解释并引导返回，多个设备同时请求也不能占两个房间。

## Answer

分支 `codex/account-12`，实现与测试见提交 `feat(rooms): enforce one active room per account across join races`。

- `RoomManager.join_or_resume` 新人分支在写入座位前检查**跨房占用**：账号在其他未结束房间已有座位时抛 `account.room-occupied`（中文「你已有未结束房间，请返回原房间。」+ `details.roomCode`），与创建路径同源；本人恢复原房优先于该检查，不算新占用。被拒连接不产生座位，占用与房态不变。
- `RoomManager` 新增占用锁：`create_room` 与 `join_or_resume` 的「占用检查 → 座位提交」成为原子步骤，创建与加入共用同一检查；多设备并发建不同房、进不同房、建房与进房混合竞争最终只有一次有效占用（单元级并发线程 + barrier 已证明无锁时同账号并发建房会产生 4 间房，加锁后收敛为 1）。
- 正常终局释放该房全部玩家占用（`room_for_account` 只认未结束房间），原房保留结果浏览；进行中断线、房主等待阶段返回大厅均保留占用与房主身份。
- 前端（`GameScreen.tsx`、`App.tsx`）：占用拒绝帧携带 `details.roomCode` 时，失败页直接提供「返回房间 XXXXXX」入口，与创建路径的大厅返回入口一致；无 roomCode 时保持返回大厅再查询的既有链路。
- 证据与验证记录见 [../evidence/12.md](../evidence/12.md)：V06.01–V06.04 全部以真实 uvicorn/HTTP/WS（独立临时存档与端口、真实线程 + barrier 并发）执行；重启验证用完整进程树终止后同存档目录重启。浏览器端多设备场景已由主 agent 外部 Chrome 实际执行并通过（占用拒绝与返回原房直达入口；纯并发时序由服务端真实线程+barrier 测试保证）。
