# 规则耦合测试补强（B9 / B7 / C2）

Status: resolved（2026-10-06 剩余验收补齐，合并至 skill-coupling-test-hardening）

主记录：[技能耦合测试补强](../skill-coupling-test-hardening/spec.md)。以下正文保留为原始需求与讨论历史；当前验收证据、golden 延期结论及测试结果见主记录末尾「2026-10-06 重复 spec 收口」，后续工作从主记录进入。

## Problem Statement

规则耦合评审（2026-10-03，30 耦合点卡片）已全部裁决并基本完成测试落地，但三个点的「见证质量」不足：将来任何人对这些路径做重构或调整时，测试套件拦不住行为漂移——

- **B9（法师 × 审判者万能标记）**：裁决为「法杖把 wild 标记变普通问号、自选色永久丧失，字面执行、有意保留」，引擎行为与裁决一致，但**没有任何测试**锁这个语义；golden 分支锁也未覆盖法师分支。
- **B7（守护者 3 点归还剑盾）**：裁决明确「含技能/反伤来源」，但唯一专项测试是**白盒**——手工把伤害置 3 再直调引擎内部的伤害后处理，从未从任何真实伤害来源（攻击/挡刀/技能/反伤）驱动到 3 点。
- **C2（3 伤志愿者挡刀自杀终局）**：裁决为「经 C1 推论**不可达**，留一致性注记」，但「不可达」本身没有被测试锁住——资格过滤一旦被人改动，这条安全推论就悄悄失效。

## Solution

三条纯测试补强，全部复用既有引擎公开命令测试缝：B9 用真实命令驱动「法师抹除 wild → 审判者亮牌不再出现色选窗」锁死语义；B7 把白盒测试替换为真实伤害来源驱动的黑盒测试；C2 用公开命令构造 3 伤玩家并断言其永不具备干涉资格、伪造表态被防御性拒绝。不改引擎、不改协议、不动 ruleset、不重生成 golden。

## User Stories

1. 作为规则引擎的维护者，我希望法师×万能标记的裁决语义有专项测试，这样将来重构法师实现时自选色丧失的行为不会被无意恢复。
2. 作为规则引擎的维护者，我希望守护者 3 点还剑盾从真实伤害来源（技能/反伤）驱动验证，这样任何改动伤害链路的人都会被测试逼着对齐「跨一切伤害源」的裁决。
3. 作为规则引擎的维护者，我希望 3 伤玩家的干涉资格不可达性有测试锁，这样资格过滤被改动导致「志愿者自杀终局」复活时会立刻红灯。
4. 作为规则引擎的维护者，我希望伪造/越权的干涉表态被防御性拒绝且不消耗 revision，这样客户端 bug 或恶意输入不会污染对局状态。
5. 作为规则引擎的维护者，我希望守护者测试断言精确的事件序列与资源清零，这样还剑盾的审计轨迹（事件日志）顺序也被确定性锁住。
6. 作为规则引擎的维护者，我希望法师测试覆盖「已亮出的 wild 标记也被改写」的分支，这样抹除已公开情报（B8 连带）的行为同样有见证。
7. 作为产品方/规则仲裁者，我希望每条补强测试都锚定语料裁决原文（B7/B9/C2 三行），这样测试、规则书、引擎三方一致性可审计。
8. 作为玩家，我希望「法杖是对抗审判者的战术手段」这一设计意图被测试固化，这样后续版本更新不会悄悄废掉这个家族策略。
9. 作为玩家，我希望挡刀投票的资格列表永远排除 rank 已亮者，这样终局不会被一条理论上不可达的自杀路径意外触发。
10. 作为负责验收后续功能的 agent，我希望这批测试进入默认测试套件并被 `unittest discover` 全量执行，这样每个新功能完成后跑套件时它们自动在场。
11. 作为关注回放确定性的维护者，我希望新测试涉及的任何引擎自动默认都遵循确定序（marker-0 → marker-1 → rank），这样测试不会引入跨进程不确定性。

## Implementation Decisions

- **纯测试批次**：不修改引擎行为、协议字段、ruleset 版本（保持 0.5），不重生成任何 golden fixture。全部断言通过公开命令 → 事件日志/公开状态完成。
- **B9 测试形态**：7 人奇数局构造法师（rank 8）与审判者（fleur-cross）。对法师造成伤害使其亮出 rank 开技能窗，发动技能指定审判者；断言：标记抹除事件发出、审判者两张身份标记变为普通问号、法杖资源发放。随后对审判者造成第 1 点伤害，其自选亮牌窗口**不再出现 wild 三色（玫/兽/问号）选择**，亮出值即问号——锁「自选色永久丧失」。
- **B9 已亮标记分支**：同一测试或姊妹测试先让审判者亮出一张 wild（走色选窗选定颜色），再被法师抹除，断言已亮的公开值也被改写为问号（语料 B8+B9 连锁）。
- **B7 测试形态**：守护者先发动技能（自己持剑、目标持盾），随后从**技能伤害**与**狂战士反伤**两个真实来源把守护者推到第 3 点；断言两次资源归还事件（剑、盾各一）、双方对应资源归零、守护关系清空、事件序列确定。原白盒测试（手工置 3 伤 + 直调内部伤害后处理）删除，由公开命令驱动版本替换；攻击来源随替换顺带转为一条公开路径；挡刀来源推到 3 点为可选加强，不强制。
- **C2 测试形态**：公开命令把一名玩家打到 3 点（第 3 点被迫亮 rank），随后匕首持有者攻击第三方；断言 3 伤玩家不出现在干涉投票开启事件的资格列表（rank 已亮过滤）；再断言其伪造 respond 干涉命令被引擎以 not-eligible 拒绝、revision 不前进。与 C1（rank 已亮者永无挡刀资格）合并构成 C2「不可达」裁决的一致性注记测试。
- **golden 锁挂起**：既有 fixtures（7/9/11 人奇数局）不含任何标记抹除事件，mage×wild 的 golden 分支锁无法在纯测试批次加入（需 runner 定向路由 → fixtures 重生成 → 按惯例伴随 ruleset bump）。挂起到下一次 bump，沿用 rule-coupling 07 的机制（runner 路由 + 分支断言）。
- **断言风格**沿用既有规则分支套件：事件类型序列精确相等、payload 精确相等、RuleError 错误码、revision 不动；涉及引擎自动默认处遵循确定序，必要时补一条跨 hash 种子一致性断言。

## Testing Decisions

- 好测试只测**外部行为**：公开命令进，事件日志与公开状态出；本批的核心价值之一就是把 B7 从白盒归位为黑盒。不直调引擎内部方法、不读取私有中间量。
- 被测范围：规则引擎的技能结算、伤害后处理、干涉资格过滤三个纯函数域；server 层与前端不涉及。
- Prior art：规则分支套件中 mage/berserker 的既有专项测试（真实命令驱动 + 精确事件断言）、诅咒分支的三方连锁测试（多技能交叉的长场景驱动）、攻击分支的资格列表测试、golden 分支锁的 fixture 文档断言风格。
- 运行入口不变：`.venv` 的 `python -m unittest discover`（不引入 pytest）。

## Out of Scope

- 引擎行为、协议、ruleset 版本的任何变更；golden fixture 重生成。
- B9 的 golden 分支锁（挂起至下一次 ruleset bump）。
- CI / 自动化流水线搭建（见 Further Notes 的事实说明）。
- 其余 27 张耦合卡的再覆盖（已有专项或不变量兜底）。
- 前端与投影层的任何改动。

## Further Notes

- 裁决依据：规则语料「产品方裁决（2026-10-03）」小节——B9 行（法杖×wild，「字面执行且作为家族对抗审判者的手段，有意保留」）、批量确认 21 条中的 B7 行（守护者 3 伤归还剑盾含技能/反伤源）与 C2 行（「经 C1 推论不可达，留一致性注记」）；相关 ADR：0006（技能伤害亮牌权）、0010（盾语义）。
- 执行保障事实：落库后进入默认后端测试套件，每次 `python -m unittest discover` 全量执行；仓库当前**没有 CI 流水线**（`.github/workflows` 仅 quota-keeper，与测试无关），「新功能完成后跑套件」依赖既有开发约定（修复须同步文档/测试/golden）。若未来要硬门禁（如部署前强制跑套件），另立工作单。
