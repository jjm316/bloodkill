# 客户端干涉决策模块深化

Workflow: 用户指定 implement 技能；按规格与既定接缝验证，完成 Standards / Spec 双轴评审后提交当前分支。

## 问题

干涉请求、干涉投票、多人自愿后选择的客户端知识分散在 GameScreen 的弹窗与偏好代发、ActionsPanel 的选择按钮、Board 的公开提示。调整一个阶段需要维护多个调用方，且回放复用 Board，不能把实时副作用带进回放。

## 已确认的实施范围

1. 将干涉三段的弹窗、等待横幅、选择按钮、两个本机偏好和自动代发收拢到同一客户端 module；GameScreen 不再解释干涉阶段、维护干涉偏好或代发窗口键。
2. 实时入口在 GameScreen 的所有条件 return 前调用，去重记录随房间页面存活，不随阶段弹窗挂载重置。
3. Board 与 ReplayScreen 共享无副作用的公开干涉提示；该提示不读偏好、不启动计时器、不发送命令。
4. 授权继续由 legalActions 驱动，客户端不重新计算资格，不根据 pending 自行创造操作权限；发送仍使用现有 useGameSocket.send。
5. 保持现有布局、CSS 类、中文文案、选择按钮的位置和顺序，保留 gate / poll / choice 与单人窗口的互斥呈现。
6. 保持两个偏好独立及现有存储键：bloodbound:no-block、bloodbound:no-assist。保留 poll 的 revision:deadline、gate 的 gate:revision:deadline 去重语义。
7. 保留攻击者点名优先取 pending.attackerPlayerId、缺失时查公开 AttackDeclared 的逻辑；不得以 daggerHolderId 猜测攻击者。
8. 共享现有倒计时实现，避免干涉模块反向依赖 GameScreen。保留服务端时间对齐、每秒刷新和卸载清理行为。
