# 干涉投票前增加被攻击者「挡刀请求」确认门控

Type: task
Status: resolved
ADR: docs/adr/0012-intervention-request-gate.md
裁决日期: 2026-10-04（产品方 grilling 裁决，Q1–Q10 全部收口）
实施完成: 2026-10-05（分支 `spec/intervention-request-gate`，issues 01–05 全部 resolved）

## Problem Statement

（以下从玩家视角描述）今天每一次匕首攻击声明后，系统立刻向所有有挡刀资格的玩家弹「是否为 X 挡刀？」——大多数时候被攻击的人根本不想要别人挡刀（甚至明知无人会挡），全桌却要陪着一个注定无结果的弹窗走完倒计时，手机上尤其骚扰。而整件事的当事人在开票前反而没有任何发言权先说一句「我不需要」。

## Solution

攻击声明后不再自动开全员投票：先**只向被攻击者**弹一个确认窗「是否需要他人为你挡刀？」——正文写明攻击者、请求与不请求的后果，并附「可为你挡刀的玩家」名单与倒计时。被攻击者点「请求挡刀」后，现有的全员公开自愿投票照常开启（投票与三选一语义零改动）；点「自己承受」或窗口超时，攻击立即在被攻击者身上正常结算，其他人全程只在事件日志里看到一行记录，不弹任何窗。另加客户端偏好「默认不让他人挡刀」：开启后连这个确认窗都不弹，自动代答不需要。当场上没有任何人有挡刀资格时（如目标持扇），确认窗静默跳过、直接结算。

## User Stories

1. As a 被攻击者, I want 攻击声明后只有我一个人收到「是否需要他人为你挡刀？」确认窗, so that 开不开投票由我决定，不再骚扰全桌。
2. As a 被攻击者, I want 确认窗正文写明是谁攻击了我、请求挡刀与自己承受分别会发生什么, so that 我在信息完整的情况下做决定。
3. As a 被攻击者, I want 确认窗里看到「可为你挡刀的玩家」名单, so that 我一眼就知道求了有没有用。
4. As a 被攻击者, I want 名单只有我自己可见, so that 我的判断过程不向他人泄露。
5. As a 被攻击者, I want 点「请求挡刀」后全员投票立即照常开启, so that 想要求助时不会因为多了一步而错过窗口。
6. As a 被攻击者, I want 点「自己承受」后攻击立即结算、不再打扰任何人, so that 拒绝是干脆的一次点击。
7. As a 被攻击者, I want 不回应时窗口到期自动视为不需要并结算, so that 掉线或离开也不会卡死全局。
8. As a 被攻击者, I want 开启「默认不让他人挡刀」偏好后确认窗不弹、自动代答不需要, so that 不想求人时连一步都省掉。
9. As a 被攻击者, I want 场上无人有挡刀资格时根本不弹确认窗, so that 一个注定无人能应的求助窗不会浪费我的时间。
10. As a 被攻击者, I want 确认请求后投票阶段的既有权利原样保留——多人自愿时我可选其一或全部拒绝, so that 看到志愿者名单后仍能改主意。
11. As a 志愿者候选玩家, I want 只有被攻击者明确请求后才收到「是否为 X 挡刀？」弹窗, so that 我面对的每一次询问都是有意义的。
12. As a 志愿者候选玩家, I want 请求之后的投票弹窗、公开唱票、答后不可反悔与今天完全一致, so that 既有博弈习惯不受影响。
13. As a 其他玩家, I want 被攻击者确认期间看到「等待 {目标} 确认是否需要他人挡刀…」横幅, so that 我知道游戏在等谁、等什么。
14. As a 其他玩家, I want 目标请求/拒绝/超时都以一行中文日志公开, so that 事后复盘能看清每次攻击为何开票或没开票。
15. As a 攻击者, I want 同样看到等待横幅与结果日志, so that 我知道自己的攻击何时、以何种方式结算。
16. As an 观众, I want 看到与玩家一致的公开事件流（横幅/日志）, so that 旁观不泄露任何私有信息、也不缺公开信息。
17. As a 房主, I want 门控窗复用我开局配置的干涉时限、不新增任何配置项, so that 开局负担不增加。
18. As a 房主, I want 开局流程与时限下拉与今天完全一致, so that 本变更对我零学习成本。
19. As a 断线重连的被攻击者, I want 重连后确认窗仍在（未过期）或已按超时结算, so that 断线不产生歧义状态。
20. As a 偏好用户, I want 「默认不挡刀」（我不为别人挡）与「默认不让他人挡刀」（我被攻击时不求人）是两个独立开关, so that 两种意愿可以自由组合。
21. As a 开发者, I want 门控建模为 intervention pending 的第三种 stage（gate → poll → choice）, so that 复用既有挂起窗、投影与超时机制，不引入新概念。
22. As a 开发者, I want 门控超时由服务端 DeadlineScheduler 代发 timeout 命令、引擎不存墙钟, so that 重放确定性约束不被破坏。
23. As a 开发者, I want ruleset 0.5 → 0.6 硬切、协议 v2 → v3、golden 重生成, so that 不出现混版本状态破坏重放。
24. As a 开发者, I want 挡刀资格集为空时静默短路前移到门控之前, so that 行为与 0.5 现有短路一致，不为无人可应的场景制造无意义的窗口与事件噪音。
25. As a 测试维护者, I want 现有投票/三选一测试只前置一条门控确认即可继续运行, so that 本变更的测试迁移成本最小。

## Implementation Decisions

- **引擎：门控阶段建模**。attack 命令完成既有校验（持盾目标拒绝、审判者 3 伤限制、匕首移交目标）后计算挡刀资格集（条件不变：未捕获、非攻击方、非目标、rank 未亮、目标未持扇）。资格集为空 → **不产生任何门控事件**、直接走现有结算路径（短路从「不开投票」前移到「不开门控」）；非空 → 进入 `kind=intervention, stage="gate"` 的 pending，actor 为被攻击者，唯一合法动作 `answer-intervention-request {need: bool}`。门控期间其余一切命令照旧被 pending 互斥拒绝。
- **协议 v3 新增契约**（协议字段英文、界面文案中文，沿用仓库约定）：
  - 命令 `answer-intervention-request`，字段 `{need: true|false}`，仅门控阶段的被攻击者合法；
  - 系统命令 `timeout-intervention` 扩展 `{stage: "gate"}`（照旧仅服务端可发，客户端直发拒绝）；
  - 事件 `InterventionGateOpened {targetPlayerId, attackerPlayerId, eligiblePlayerIds}`；
  - 事件 `InterventionGateAccepted {targetPlayerId}`，随后紧跟既有 `InterventionPollOpened`（字段不变）；
  - 事件 `InterventionGateDeclined {targetPlayerId, reason: "target-declined"|"timeout"}`，随后攻击在原目标结算（复用现有无人自愿结算路径）；
  - 错误码新增 `intervention.not-gate`（非门控阶段发出）、`intervention.not-target`（非被攻击者发出）；
  - pending 投影新增 `stage: "gate"`，含 `eligiblePlayerIds` 与服务端注入的 `deadline`；`responses`/`volunteerPlayerIds` 仅 poll 之后存在。
- **超时语义（Q1:A）**：门控到期未答 = 视为不需要，发 `InterventionGateDeclined(reason="timeout")` 并结算；与现有「投票超时视为不干涉、三选一超时全部拒绝」同一哲学。
- **门控时限（Q2:A）**：复用房主开局配置的干涉超时（30/60/90/120/180，默认 90），**不新增配置项**；门控、投票、三选一三个窗口各自独立起算（与今天 poll/choice 各自重臂一致）。
- **投票与三选一零改动（Q5）**：全员弹窗、实时公开唱票、答后不可反悔、无人自愿正常结算、恰一人自愿强制成立（被攻击者无权拒绝）、多人自愿目标可选其一或全部拒绝——全部原样保留。
- **服务端窗口调度**：deadline 调度器认第三种窗口身份 `stage="gate"`；门控按答案接力（开票则重臂 poll 窗，结算则走结算链）；重启后已过期的门控窗照旧立即补发 timeout。
- **客户端**：
  - 新增门控弹窗层（复用既有通用确认弹窗与倒计时钩子），仅当自己视角 `legalActions` 含 `answer-intervention-request` 时挂载；
  - 文案（Q6 已拍板）：标题「是否需要他人为你挡刀？」，正文「{攻击者名} 对你发起攻击。请求挡刀将向所有有资格的玩家发起询问；若不需要或超时，你将承受这次攻击。」，名单行「可为你挡刀的玩家：{名字列表}」，按钮「请求挡刀 / 自己承受」，倒计时「（剩 N 秒）」；
  - 等待期横幅复用既有挂起横幅：「等待 {目标名} 确认是否需要他人挡刀…」；
  - 事件日志四条中文：开窗「{目标} 正在确认是否需要他人挡刀」、请求「{目标} 请求他人挡刀」、拒绝「{目标} 拒绝了他人挡刀」、超时「{目标} 未确认是否需要挡刀，视为不需要」；新事件归入「干涉」类别；
  - 新偏好（Q7/Q10:A）`bloodbound:no-assist`「默认不让他人挡刀」：开启后门控窗不弹、自动代发 `need:false`，以窗口 revision+deadline 为键防重复代发；与既有「默认不挡刀」并排为两个独立开关；纯客户端偏好，不进对局事件历史（沿用 0002 偏好哲学）；
  - 帮助文案（helpContent）挡刀流程补门控说明。
- **版本硬切**：ruleset 0.5 → 0.6（旧存档显式拒绝，同先例）；协议 v2 → v3（hello 版本不匹配照旧拒绝，旧客户端不可用）。
- **golden**：确定性走查器补门控策略——保证「接受开票」路径进 fixture（投票分支覆盖保持），拒绝路径混入；golden 6–12 全部重生成。
- **文档四同步**：规则语料追加 2026-10-04 裁决段、`intervention.poll` 前提改写、新增 `intervention.gate` 规则行（本批已先行落盘）；ADR 0012（本批已先行落盘）；CONTEXT.md 词条（本批已先行落盘）；helpContent（随实施）。

## Testing Decisions

- **好测试只测外部行为**：命令进、事件/状态出；投影按 viewer 断言可见性；前端锚定渲染文案与发送的命令。不测内部函数结构。
- **接缝全部复用既有接缝，无新增**：
  1. **引擎命令层（主接缝）**：资格集非空开窗/为空静默跳过且零门控事件；目标独占合法性（他人发答、非门控阶段发答 → `intervention.not-target`/`not-gate`）；`need=true` → GateAccepted + PollOpened 接力；`need=false` → GateDeclined(target-declined) + 立即结算（伤害、亮牌窗、技能窗照常）；超时命令 → GateDeclined(timeout) + 结算；门控期间其余命令被拒；**现有全部投票/三选一用例前置一条 `answer-intervention-request {need:true}` 即可复用**（测试助手同步）。
  2. **投影层**：gate 阶段仅被攻击者持有应答动作；`eligiblePlayerIds` 与 `deadline` 下发；观众视图无私密泄露。
  3. **服务端同步**：门控窗口被跟踪并写入 meta；投影携带 `pending.deadline`；静默到期由调度器结算；接受后接力 poll 窗；重启后过期门控窗立即补发。
  4. **golden**：6–12 重生成后字节锁重新成立；新增门控接受/拒绝两分支进分支覆盖锁；规则分支覆盖文档补行。
  5. **前端 vitest**：门控弹窗渲染条件/标题/正文/名单行/按钮命令/倒计时；`no-assist` 代发与防重复；四条日志文案与事件类别；helpContent 关键词；门控窗与单人窗口层互斥关系同步断言。
  6. **e2e 手动验收**（仓库惯例，chrome-devtools 驱动）：完整走一遍「攻击 → 门控确认 → 开票 → 挡刀成立」与「攻击 → 拒绝 → 直接结算」，多视角核对横幅/日志/无泄露。
- **先例**：引擎规则分支测试的干涉段、DeadlineWindowTests、投影测试、eventLog 与 helpContent 的 vitest 模式、既有 e2e 驱动脚本配方。

## Out of Scope

- 投票与三选一阶段的任何语义改动（公开唱票、恰一人强制成立、可选其一或全拒——2026-09-04 已裁，不再翻案）。
- 保密唱票（0002 Considered Options 已否决，本次不动）。
- ruleset 0.5 存档的兼容迁移（硬切，进行中对局作废重建）。
- 「默认不挡刀」志愿者侧偏好的行为变更（仅并排新增目标侧开关）。
- 门控窗独立时限配置（复用干涉超时，不加配置项）。
- 两个偏好合并为「免打扰」总开关（Q10:B 已否决）。
- 技能伤害路径（照旧永不触发干涉，自然也永不开门控）。

## Further Notes

- **裁决时间线**：来源 C 原文「仅攻击目标可请求干涉」→ ADR 0002（2026-09-04）改为攻击后自动全员公开自愿投票 → 本裁决（2026-10-04）折中回归：目标确认门控在前、全员投票在后。0002 的核心遗产「承伤同意权归干涉者本人」在新模型原样存活，0012 只取代「自动开启」这一点。
- **grilling 结论一览**：Q1 否定/超时=不需要立即结算（A）；Q2 门控时限复用干涉超时配置（A）；Q3 资格集空静默跳过；Q4 三处公开+归「干涉」类别；Q5 投票/三选一零改动；Q6 弹窗文案按推荐；Q7 增加目标侧「默认不让他人挡刀」偏好；Q8 命名套装（干涉请求/stage gate/answer-intervention-request/三事件）；Q9 ADR 0012 + 语料 + 词条 + helpContent 四同步；Q10 两偏好独立开关（A）。
- **命名考古注意**：0002 时代删除的旧命令 `request-intervention`（目标点名模型）与旧规则 ID `intervention.request` **不复用**，新命令/新规则 ID 均为独立命名（`answer-intervention-request` / `intervention.gate`），避免考古混淆。
- **技能产物公开性旁路裁决（2026-10-04，同日另一会话）**：扇、法杖、真/假诅咒、盾、剑、羽毛等技能产物状态在设计上一律公开（「被贴了扇子，所有人都应该知道」）。本 spec 已据此剔除「静默短路防扇泄露」旧理由——Q3 的跳过仅以 UX 成立。该裁决尚未写入规则语料；引擎/投影/前端三层的存量公开性差距核查仍在别线待办，如立新单与本 spec 互不阻塞。
- **上线影响**：测试房间在部署后作废重建；旧客户端被协议 v3 拒绝，需同步更新前端。
- **词表已随本 spec 批次先行更新**：CONTEXT.md 新增「干涉请求」条目、改写「干涉投票」「干涉超时」条目。
