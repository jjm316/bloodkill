# 账号功能评审后清理：三处重复与一处脆弱启发式

Status: resolved
日期：2026-10-17
来源：分支 `codex/username-password-accounts`（对照 `master`，55 提交）的两轴代码评审，Standards 轴三条判断性发现。本 spec 只收编这三条；评审其余发现（Spec 轴三项缺口、其余代码味道）不在本 spec 范围内。
性质：纯清理重构。除下述「错误码对齐」一处明确豁免外，不改变任何对外行为语义。

## 问题陈述

账号功能合入后，同一条业务规则和同一段管线逻辑在多个入口各写了一份：

1. **密码形状规则重复三份**。账号模块的校验器写了一份「6–12 个字符」规则与中文提示；管理 HTTP 重置接口又内联写了一份；管理 CLI 的交互式新密码提示再写一份。三处文案与判定已经出现细微漂移的风险（CLI 的重试提示与校验器消息措辞不同），将来改规则（比如放宽到 6–20）要记得改三处，漏一处就出现「服务端接受、管理面拒绝」或反过来的不一致。
2. **连接终止管线重复五处**。退出登录、修改密码、管理重置停连、旁观转玩家停旁观、管理关房五条路径，各自手写「按条件过滤连接注册表 → 逐条发中文原因帧 → 关闭」的同一形状；此外「从注册表按对象移除连接」的扫描在终止函数内部与退座路径里各写一遍。
3. **创建房间失败提示靠中文字符嗅探**。前端创建房间的 catch 里用「错误消息里是否含 CJK 字符」猜测这条消息是不是来自服务端——是就原文展示，不是就显示本地兜底文案。这是一个内容启发式：服务端将来发出不含中文的错误消息（或本地路径抛出含中文的异常）时，提示行为就会错。

从用户视角：玩家与管理员不会直接看到这些重复，但会承受它们的后果——不同入口对同一条规则给出不一致的提示，或创建房间失败时看到错误的文案。

## 方案

- 密码形状规则收敛到账号模块已有的单参校验器，作为唯一权威：管理 HTTP 重置接口改为捕获该校验器抛出的账号错误并透传其错误码与中文消息；管理 CLI 的提示循环复用同一校验器与同一消息，不再自带判定。
- 服务端新增一个谓词驱动的连接终止助手：按条件挑选已建立连接，逐条发指定的中文原因帧并关闭。五条重复路径全部改走该助手，各路径的中文文案与错误码保持不变。退座确认路径因发送的是确认帧而非错误帧，不并入该助手，仅复用「从注册表移除连接」的最小公共部分。
- 前端解析服务端错误帧时抛出带错误码的结构化错误类型，与网络失败等本地异常区分；创建房间失败提示据此判定来源，废除 CJK 嗅探。

## 用户故事

1. 作为玩家，我希望注册、改密、管理重置三条路径对「密码须为 6–12 个字符」给出完全一致的判定与中文提示，这样无论从哪个入口设密码都不会遇到互相矛盾的规则。
2. 作为玩家，我希望修改密码后其他设备的连接收到同一套中文终止说明，这样不管代码里终止逻辑收敛到哪里，我看到的产品行为完全不变。
3. 作为玩家，我希望创建房间失败时：服务端给了中文原因就原文展示，网络断了就显示本地兜底文案，这两者永远不会被搞混。
4. 作为玩家，我希望本次清理不改变任何我能感知的行为（会话保留时长、座位保留、广播顺序、房间关闭流程都原样），这样清理对我不可见。
5. 作为运维管理员，我希望管理 CLI 提示我输入新密码时的规则说明与服务端实际校验永远一致，这样 CLI 说合法的密码提交后不会被服务端拒绝。
6. 作为运维管理员，我希望管理重置密码接口对非法输入仍返回明确的中文原因，这样我操作的每一步都有可理解的反馈。
7. 作为维护者，我希望改密码规则时只改一处，这样规则演进不会留下半新半旧的三份拷贝。
8. 作为维护者，我希望新增「按条件停一批连接」的需求时只调用一个助手，这样第七条终止路径不会成为第六份手写拷贝。
9. 作为维护者，我希望前端判断「错误消息来自服务端」靠类型而不是靠消息内容，这样服务端错误文案的任何演进都不会破坏提示逻辑。

## 实现决策

1. 密码形状校验以账号模块现有的单参校验函数为唯一权威（其「确认密码一致」的包装照旧）；管理 HTTP 重置接口删除内联判定，改为捕获账号校验错误并按其错误码与中文消息返回 400。
2. **错误码对齐（本 spec 唯一的行为变更豁免）**：管理重置接口对非法密码的错误码由管理面通用请求码改为账号校验器自身的密码错误码。理由：该接口的消费者只有自家管理 CLI，且 CLI 只展示中文消息不消费错误码；接口仅回环可达。钉住旧码的既有测试同步更新，并在提交说明中注明该码变更。
3. 管理 CLI 与服务端同属一个 Python 包部署在同一主机，CLI 直接导入账号校验器复用判定与消息，不通过 HTTP 预检；服务端照旧权威复校，CLI 校验仅为提前反馈。
4. 终止助手按谓词挑选连接并逐条终止，返回终止数；五条路径（退出登录、修改密码、管理重置停连、旁观转玩家停旁观、管理关房）迁移后各自的错误码、中文文案、排除参数（如不停当前设备连接）语义不变。
5. 退座路径只复用「按连接对象从注册表移除」的最小公共部分，不强并入终止助手（它发确认帧不发错误帧）。
6. 前端结构化错误类型携带服务端错误帧的错误码与消息；创建房间流程在解析到服务端错误帧时抛该类型，catch 按类型分流，本地兜底文案保持原文。
7. 不引入新模块或新抽象层：终止助手放在连接注册表所在的模块；前端错误类型放在现有 API 调用所在的模块。

## 测试决策

- 只测外部行为，不测实现细节；三组改动各自落在既有测试缝合上，**不新增任何缝合**。
- 服务端沿用 `tests/` 下的 unittest 套件与 `python scripts/check.py`：密码路径以账号/管理 CLI/管理接口既有测试为基准，补充「三个入口对同一非法密码给出同一中文消息」的回归用例；终止管线以退出登录/改密/关房/旁观既有测试为基准，锁定五条路径的错误码与中文文案不变。
- 客户端沿用同目录 vitest 套件（大厅组件已有测试文件），补两个用例：服务端错误帧原文展示；网络失败（非结构化异常）显示本地兜底文案。
- 先例：修改密码端点既有「捕获账号错误并透传错误码」的测试模式可照搬到管理重置接口。

## 范围外

- 评审 Standards 轴其余判断性发现：handler 前导样板重复、`seat_accounts` 命名、广播路径上的同步 SQLite 调用等——不在本 spec，将来另行立项。
- 评审 Spec 轴三项缺口（坏旧存档切换静默跳过、管理关房部分失败状态误报、用户名字符集比「中文」窄）——独立缺陷，不属于清理。
- 前端其余 fetch 调用点向新错误类型的迁移——本 spec 只落创建房间一处，证明模式成立；其余调用点待后续需要时迁移。
- 协议版本号、golden 回放、任何规则语料相关的行为——一律不动。

## 补充说明

- 三条发现互相独立，拆为三张无阻塞依赖的工单，可并行实施。
- 本 spec 的验收基准是「行为不变（除决策 2 的错误码对齐）+ 重复消除」，不是「重写」：能不动的地方不动，测试增量最小化。
