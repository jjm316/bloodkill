# 干涉投票前增加被攻击者确认门控（intervention request gate）

ADR 0002（2026-09-04）把干涉定为「攻击声明后自动向全部有资格玩家开启公开自愿投票」。实际使用暴露出骚扰问题：大多数攻击的目标并不想要他人挡刀（甚至明知无人会挡），全桌却要陪着一个注定无结果的弹窗走完倒计时，而当事人在开票前没有任何发言权。产品方 2026-10-04 裁决折中：攻击声明后先开**仅被攻击者可见**的挡刀请求确认窗（干涉请求），目标答「请求挡刀」才开启全员投票；答「不需要」或窗口超时，攻击立即在原目标身上正常结算。挡刀资格集为空时（如目标持扇）确认窗静默跳过。

来源 C 原文「仅攻击目标可请求干涉」的精神由此部分回归，但 0002 的核心裁决原样保留：承伤同意权仍归干涉者本人——恰一人自愿时干涉必然发生（目标无权拒绝）、多人自愿时目标可选其一或全部拒绝、表态实时公开且答后不可反悔。本 ADR 只取代 0002 的「自动开启」一点，0002 整体保持 accepted。

## Considered Options

- **门控超时视为「需要」、保底开投票**：被否决——超时兜底会把门控想省掉的全员弹窗原样带回，与超时哲学（投票超时视为不干涉、三选一超时全部拒绝）相悖。
- **门控窗独立时限配置**：被否决——多一个房主配置项换不来对应对价，复用房主已配置的干涉超时（30/60/90/120/180，默认 90）。
- **复活旧命令名 `request-intervention`**：被否决——0002 时代的该命令是「目标点名强制承伤」语义，与布尔门控不同义；新命令 `answer-intervention-request`、新规则 ID `intervention.gate` 均独立命名，避免考古混淆。
- **合并「默认不挡刀」「默认不让他人挡刀」为一个免打扰总开关**：被否决——两个偏好作用对象不同（志愿者侧/被攻击侧），存在只想要其一的中间态。

## Consequences

- ruleset 0.5 → 0.6 硬切（进行中旧存档显式拒绝，同先例）；协议 v2 → v3（新增 `answer-intervention-request` 命令、`timeout-intervention` 的 gate 取值、三个 `InterventionGate*` 事件与 `stage:"gate"`；旧客户端被拒）。
- 投票与三选一语义零改动；志愿者侧「默认不挡刀」偏好原样，新增目标侧「默认不让他人挡刀」纯客户端偏好（localStorage 代发 `need:false`，不进对局事件历史，沿用 0002 偏好哲学）。
- 资格集为空的静默短路前移到门控之前，与 0.5 现有行为一致；跳过的理由是 UX——无人可应的求助窗没有意义（原「防扇信息泄露」理由作废：同日产品方裁决技能产物状态一律按公开信息对待，扇持有全员可知；产物公开性的存量核查另行处理）。
- 门控结果（请求/拒绝/超时）对全员公开记入事件日志，归「干涉」类别；等待期横幅公开。
- 语料 `intervention.poll` 前提改写、新增 `intervention.gate` 行（2026-10-04 裁决段）；CONTEXT.md 词表同步。
