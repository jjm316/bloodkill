# 用用户名密码账号建立房间参与者身份

原方案以用户填写的姓名认领房间座位，同名连接可接管座位，房主权限另由浏览器保存的令牌证明；用户难以理解进入顺序，也难以确认当前是谁的身份。2026-10-12 用户决定引入用户名密码账号，用户名就是登录账号，密码自行设定，登录后可以创建或加入房间；这重新打开旧首版规格排除账号体系的范围，以增加注册登录步骤换取明确的账号身份。

同日第一轮访谈已确认：开放用户名密码注册，用户名全局唯一、固定且同时用于公开展示；房主权限与玩家座位归属于账号，相同账号可以跨设备恢复，一个账号同时最多占据一个未结束房间的玩家座位，在线旁观也要求登录。新机制启用时停止旧房间继续游戏并保留历史回放，不按旧姓名自动认领账号。

产品方明确决定延续好友游戏的 HTTP/WS 部署，并接受密码或会话可能被截获的风险；HTTPS/WSS 不作为本次公网启用条件。此决定只限定传输与部署范围，密码存储与账号校验仍按账号功能实现。

第二轮已确认同一座位由新连接接管，普通玩家在等待阶段可退座、对局中断线保留座位，本次不增加房主解散操作。备忘及偏好按账号隔离但继续只存于本设备；任何已登录用户知道房间号即可查看已结束对局的公开回放。

第三轮已确认：房主在等待阶段离开仍保留座位与管理身份；弃局由产品方通过管理工具手动关闭并释放全员占用，工具须与账号功能一起实现并交付用法。账号有未结束玩家座位时不能同时旁观其他房间，已结束回放仍可查看。

管理关闭不伪造正常终局或胜负，未结束旧房间备份后停用，只保留已结束旧回放。登录有效期从成功登录起固定 30 天；主动改密保留当前登录、撤销其他登录，人工重置撤销全部登录，但均不改变座位归属。

本 ADR 接受上述身份模型与范围决策；完整行为、验收及计划的管理命令见 [规格](../../.scratch/username-password-accounts/spec.md)。Q1–Q26 已确认，用户要求后续将账号功能与管理工具一起实现，但当前“写好 spec 就行，先别开始做”；规格与实施议题已完备，等待后续明确启动指令，账号方案尚未实现。
